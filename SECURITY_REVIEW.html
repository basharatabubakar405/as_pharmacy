1. Objective

This review audits the AS Pharmacy backend for common web application security vulnerabilities, following the OWASP Top 10 methodology. The goal is to identify insecure coding practices, rate their severity, and provide concrete remediation steps.

3. Findings

Critical Hardcoded Database Credentials

Files: api/config.php (line 24), api/setup.php (lines 10–14)  ·  OWASP A05:2021 – Security Misconfiguration / CWE-798

Database host, port, username, and password are hardcoded directly in source files committed to a public GitHub repository:

define('DB_PASS', '••••••••••••••••••••••••••••••••');

Anyone who views the repo has full read/write access to the live database — including editing user accounts, deleting sales records, or dumping the whole users table.

Remediation:
  • Rotate the MySQL credentials immediately (the current ones are compromised since they're in a public repo history).
  • Move all credentials to environment variables (getenv('DB_PASS')) injected via Railway's environment variable settings, never committed to Git.
  • Purge the old credentials from Git history (e.g. with git filter-repo), since rotation alone doesn't remove them from old commits.

Critical Plaintext Password Storage & Comparison

Files: api/auth.php (lines 28, 61, 116–117), api/users.php (lines 39, 60), api/setup.php (line 93)  ·  OWASP A02:2021 – Cryptographic Failures / CWE-256

Passwords are stored and compared as plain strings:

if (!$user || $user['password'] !== $password) { ... }

Seeded default accounts even use trivial passwords (admin / staff). If the database is ever leaked, every user's real password is exposed instantly — a serious problem since people frequently reuse passwords across sites.

Remediation:
  • Hash all passwords with password_hash($password, PASSWORD_BCRYPT) at registration/reset time.
  • Verify logins with password_verify($input, $user['password']) instead of !==.
  • Force a password reset for all existing accounts after migrating, since old plaintext values can't be un-hashed.
  • Replace seeded default passwords with strong, unique values, and prompt for change on first login.

High Broken Access Control (No Authorization Checks)

Files: api/users.php, api/medicines.php, api/sales.php, api/settings.php, api/attendance.php  ·  OWASP A01:2021 – Broken Access Control / CWE-862

Every state-changing endpoint (POST, PUT, DELETE) only checks session_start() — it never verifies who is logged in or what role they have before executing. For example, users.php's DELETE case will delete any user by ID for any visitor with an open session, staff or not. The role field is only checked client-side in components.js to hide/show UI buttons — that's cosmetic, not security, since any user can call the API endpoints directly regardless of what the UI shows them.

Remediation:

Add a shared authorization helper in config.php, called at the top of every privileged action:

function requireRole($role) {
    if (empty($_SESSION['user_id']) || $_SESSION['role'] !== $role) {
        respond(['error' => 'Forbidden'], 403);
    }
}
  • Store role in the session at login (currently only user_id is stored), and check it server-side before any write/delete operation.
  • Never trust role information sent from the client in a request body.

Medium Publicly Accessible Database Installer

File: api/setup.php  ·  OWASP A05:2021 – Security Misconfiguration

setup.php is reachable at a public URL and re-creates tables / reseeds default admin credentials without any authentication. If tables are ever dropped, anyone who finds this URL can re-run it and get a system with known default logins.

Remediation:
  • Delete or move this script out of the web root after initial deployment.
  • If it must stay, protect it with a one-time setup token or IP allowlist, and make it exit immediately if users table already has rows.

Medium Overly Permissive CORS Policy

Files: api/config.php (line 12), .htaccess (line 10)  ·  OWASP A05:2021 – Security Misconfiguration
header('Access-Control-Allow-Origin: *');

This allows any website to make authenticated requests to the API from a user's browser, which widens the attack surface for cross-origin data theft, especially combined with the missing access-control checks above.

Remediation:
  • Restrict Access-Control-Allow-Origin to the actual frontend domain only (e.g. https://aspharmacy-production.up.railway.app), not *.

Good Practice Positive Findings

  • All database queries use PDO prepared statements with bound parameters — no raw string interpolation into SQL was found. This effectively prevents classic SQL Injection across medicines.php, sales.php, attendance.php, users.php.
  • sanitize() in config.php applies htmlspecialchars + strip_tags, a reasonable baseline against stored XSS, though it isn't consistently called on every input field — worth auditing per-endpoint.
  • Security response headers (X-Content-Type-Options, X-Frame-Options, CSP, etc.) are already configured in config.php, which many student projects skip.

5. Recommendations (Priority Order)

  • Rotate DB credentials + move to environment variables — do this first, since the current ones are already public.
  • Migrate to password_hash()/password_verify() and force password resets.
  • Implement server-side session-based role checks on every write/delete endpoint.
  • Remove or lock down setup.php.
  • Tighten CORS to the real frontend origin.

6. Conclusion

AS Pharmacy demonstrates solid fundamentals in SQL injection prevention (consistent use of PDO prepared statements) and has some security headers already in place. However, credential management, password storage, and authorization are the weakest areas and should be treated as the immediate next milestone before any further feature work or redeployment.
